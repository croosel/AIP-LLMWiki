# 蜂群決策映射

> 蜜蜂蜂群在數百萬年的演化中發展出高效的集體決策機制。Scout-then-Swarm 將這套生物智慧映射到多 LLM Agent 協作架構中，但並非生搬硬套——而是識別出哪些生物機制可直接移植、哪些需要改造、哪些必須摒棄。

## 生物學基礎

### 蜂群決策的四個階段

蜜蜂蜂群在選擇新巢址時，展現出令人驚嘆的集體智慧：

1. **偵查蜂（Scout）**：僅佔蜂群 3-5% 的經驗蜜蜂外出偵查，各自獨立搜索潛在巢址
2. **搖擺舞（Waggle Dance）**：歸巢的偵查蜂透過搖擺舞傳達巢址方向和品質，舞蹈強度與巢址品質成正比
3. **交叉驗證（Cross-Verification）**：被招募的蜜蜂親自前往驗證，而非盲目信任舞蹈
4. **法定人數（Quorum）**：當某個巢址的蜜蜂數達到閾值（約 10-20 隻），該巢址被確定

### 蜂群決策的核心特性

| 特性 | 說明 |
|------|------|
| 獨立偵查 | 每隻偵查蜂獨立搜索，不受其他蜂影響 |
| 品質信號 | 搖擺舞的強度和持續時間反映巢址品質 |
| 正反饋 | 好巢址吸引更多蜜蜂 → 更多舞蹈 → 更多蜜蜂 |
| 自我修正 | 親自驗證機制防止錯誤擴散 |
| 收斂決策 | 法定人數閾值確保決策不過早也不過晚 |

## 技術映射表

| 蜂群機制 | 技術實現 | 說明 | Wiki 先驗原型 |
|---------|---------|------|-------------|
| 偵查蜂（Scout） | Orchestrator + Experience DB 搜尋 + 模板匹配 | 帶經驗做任務分析和拆解 | PAP Stage 1-2 + P0 指揮官 |
| 排程蜂（Orchestrator） | DeepSeek V4 Pro + 分解覆核檢查 | DAG 任務圖生成 + 耦合度判斷 | 3-Phase 主 Agent |
| 工蜂（Worker Bee N） | LiteLLM 並行調用，按子任務類型路由模型 | 各模型執行不同子任務 | 3-Phase Phase 2 並行 Agent |
| 搖擺舞（Waggle Dance） | 結構化辯論：紅隊質詢 + 倡議蜂回應 + 交叉授粉 | 取代純正反饋，防止馬太效應 | — |
| 裁判蜂（Judge） | Qwen 3.7 Max 交叉驗證 + 加權融合 | 不參與執行，獨立審計 | OPC 質檢總監 |
| 法定人數（Quorum） | 置信度 >= 0.6 + 領先第二名 1.5 倍 + 無致命缺陷 | 三條件同時滿足才收斂 | — |
| 經驗回寫（Learn） | SQLite + FTS + TTL + 強制探索 | 成功經驗沉澱，過期自動清理 | 經驗反饋閉環 |

### 映射的關鍵差異

並非所有蜂群機制都能直接映射。最重要的修正：

| 生物機制 | 直接映射的問題 | 技術修正 |
|---------|-------------|---------|
| 搖擺舞正反饋 | 馬太效應：早期錯誤被放大 | 結構化辯論 + 紅隊質詢 |
| 蜜蜂獨立搜索 | LLM 的答案空間是無限維度的，非離散選項 | 模板匹配限制搜索空間 |
| 親自驗證 | LLM 無法「親自」感知物理世界 | 交叉驗證（不同模型驗證） |
| 法定人數 | 蜜蜂數量有限，LLM 答案是連續的 | 置信度閾值 + 相對領先度 |

## 為什麼搖擺舞需要被修正

審稿蜂的攻擊揭示了純正反饋（waggle dance）在 AI 系統中的致命問題：

### 馬太效應

三個 worker 模型回答同一個問題。MiniMax M3 第一個返回答案，品質 60 分。搖擺舞機制給它初始權重。Qwen 3.7 Max 第二個返回，品質 80 分，但因為 M3 已經累積了正反饋，Qwen 的權重被壓低。**先返回的答案不代表更好，只代表模型推理更快。**

### 贏者通吃壓制少數派

假設三個模型分析一段程式碼：
- M3 和 K2.7 都認為「這段程式碼沒有 bug」（多數派）
- Qwen 3.7 Max 認為「有一個 race condition」（少數派）

搖擺舞的正回饋會讓多數派意見被放大。但在程式碼審查中，**少數派的警報往往是正確的**——bug 通常就是大多數人忽略的那個。

### 類比失效

蜜蜂是在物理世界中做選擇（這朵花有蜜 vs 那朵花有蜜），選項有限，評估標準單一。LLM 協作是在無限維度的答案空間中做融合，評估標準多維且模糊。**把生物類比直接搬到 AI 系統，是一種概念上的偷懶。**

## 結構化辯論取代搖擺舞

修正後的「擺尾舞」是一個**結構化辯論協議**：

### 角色定義

| 角色 | 職責 | 實現 |
|------|------|------|
| Scout（偵查蜂） | 各自獨立提出解決方案方向 | 不同 Worker Bee |
| Advocate（倡議蜂） | 為某個方向辯護，闡述優勢 | 提出該方向的 Scout |
| Red Team（紅隊蜂） | 嘗試找出每個方向的缺陷 | Qwen 3.7 Max (Judge) |
| Quorum Counter | 統計收斂條件是否滿足 | 程式邏輯，非 LLM |

### 防馬太效應機制

| 機制 | 如何防止 | 參數 |
|------|----------|------|
| 置信度上限 | 即使方向再好，也不能完全確定 | 0.8 |
| 強制紅隊 | 每個方向都必須被質疑 | 每輪必執行 |
| 衰減函數 | 未被再次確認的方向逐漸失去權重 | 每輪 -15% |
| 交叉授粉 | 鼓勵合併而非贏者通吃 | 嘗試方向合併 |
| 探索預算 | 保留資源給非主流方向 | 至少 20% |

### 法定人數收斂條件

三條件**同時滿足**才收斂：

1. **絕對置信度**：領先方向的置信度 >= 0.6
2. **相對領先度**：領先方向的置信度是第二名的 1.5 倍以上
3. **無致命缺陷**：紅隊沒有標記任何致命缺陷

最大 3 輪辯論。若 3 輪後仍未收斂 → 強制收斂 + 標記 `needs_human_review`。

> 注意：MVP 階段擺尾舞被禁用（`waggle_dance.enabled: false`），Phase 2 才實作。MVP 的核心假說是「交叉驗證融合」而非「擺尾舞」。

## 三種執行模式

基於 [[Agent并行架构]] 的依賴拓撲分析法，Scout-then-Swarm 定義了三種執行模式：

### Swarm 模式（低耦合 — 子任務完全獨立）

```
Task Graph → [Worker A ∥ Worker B ∥ Worker C] → Self-Check → Synthesizer → 輸出
```

適用場景：程式碼審查（靜態分析、邏輯審查、風格檢查平行進行）

### Pipeline 模式（高耦合 — 子任務有線性依賴）

```
Task Graph → Stage 1 → Checkpoint α → Stage 2 → Checkpoint β → Stage 3 → 輸出
```

適用場景：需求分析 → 程式碼實現 → 測試生成

### Checkpoint 模式（混合 — 階段內平行，階段間順序）

```
Task Graph → [Phase 1: A ∥ B ∥ C] → Checkpoint γ → [Phase 2: D ∥ E] → Checkpoint δ → Pipeline Stage 3 → 輸出
```

適用場景：前端元件開發（多元件平行）→ 整合測試（依賴所有元件）

### 耦合度判斷規則

```python
def determine_coupling(task_graph):
    output_deps = count_output_as_input_edges(task_graph)
    if output_deps == 0:
        return "low"      # → Swarm
    elif output_deps <= len(task_graph.nodes) * 0.3:
        return "medium"   # → Checkpoint
    else:
        return "high"     # → Pipeline
```

不確定時預設 Pipeline（寧可慢，不要錯）。只有經驗庫命中高置信度經驗時才用 Swarm。

## Fast-Track 快速通道

80% 的任務不需要完整四階段流程。Fast-Track Gate 在 50ms 內決定任務複雜度：

```python
class FastTrackGate:
    FAST_TRACK_TEMPLATES = {
        "translation":        {"model": "kimi-k27-code",   "reason": "中文理解強"},
        "summarization":      {"model": "minimax-m3",     "reason": "長文本處理"},
        "code_snippet":       {"model": "kimi-k27-code",   "reason": "程式碼生成"},
        "structured_extract": {"model": "qwen-37-max",    "reason": "結構化輸出"},
        "reasoning_step":     {"model": "deepseek-v4-pro", "reason": "推理最便宜"},
    }
```

延遲預算：
- Fast-Track 分類：< 50ms
- 簡單任務直達：< 2s
- 複雜任務完整流程：< 30s（P95 < 15s 為 MVP 目標）
- 目標：80% 的請求走 Fast-Track

## 連接第一性原理評估

蜂群決策的最終品質驗證仍需要第一性原理檢查。但審稿蜂指出「通用第一性原理評估」對開放式任務無效，因此 Scout-then-Swarm 改為**任務類型感知**的評估策略：

| 任務類型 | 評估策略 | 核心檢查項 |
|---------|---------|----------|
| 分析型 | 一階原則 | 邏輯自洽？覆蓋所有要求？有事實錯誤？ |
| 程式碼 | 可執行性 | 能編譯/執行？處理邊界？有安全漏洞？ |
| 創意型 | 約束符合性 | 符合風格/調性？有 AI 味？偏離主題？ |

這確保了蜂群決策的每一步都經過適當的品質門檻，而非一刀切的通用評估。
