## 架构决策记录

**决策**：在现有 4 总监架构基础上，新增独立的"质检总监"（QA Inspector），形成 5 总监架构。质检总监不隶属于任何业务总监，直接向 CEO 汇报，对所有任务的产出物行使独立审计权。

**决策理由**：现有架构中所有质量检查依赖人类 CEO 审核（前期 100%、后期 30%），CEO 将成为规模化后的最大瓶颈。独立质检 Agent 可以将 CEO 从逐项审核中解放出来——质检 Agent 先做标准化审计，CEO 只需关注"质检通过但有战略影响"的决策和"质检未通过"的回滚审批。

**核心原则**：每个任务在启动前必须定义可衡量的"任务目标"，该目标自动成为审计 Agent 的评分标准。审计不合格 → 回滚 → 重新制定执行方案 → 重新执行 → 重新审计。

## 一、新架构：5 总监 + 独立质检层

```
CEO（人类）—— 战略 + 最终审批
  |
  +-- 质检总监 (QA Inspector, 1 AI Agent)  ←—— 新增
  |     +-- 审计组 (1-2 AI Agent)
  |     |
  |     [独立于所有业务线，不参与执行，只做审计]
  |
  +-- 内容总监 (AI) —— 统筹内容生产
  |     +-- 文案组 / 图片组 / 视频组 / 社媒组
  |
  +-- 独立站建站总监 (AI) —— 统筹建站全流程
  |     +-- 建站组 / SEO-GEO组 / 运维组
  |
  +-- 运营总监 (AI) —— 国际站运营
  |     +-- SEO组 / 广告组 / 数据组 / 国际站组
  |
  +-- 客服总监 (AI) —— 客户服务
        +-- 邮件组 / 聊天组 / 退货组
```

**Agent 数量更新**：原 17-21 Agent → 现 **19-24 Agent**（新增质检总监 1 + 审计组 1-2）。

**质检总监与四大总监的关系**：平级、独立、不交叉。质检总监不参与任何执行决策，四大总监不干涉审计标准。当审计结果产生分歧时，CEO 是最终仲裁者。

## 二、质检总监的角色定义

| 维度 | 定义 |
|------|------|
| **角色名称** | 质检总监（QA Inspector Director） |
| **Agent 数量** | 1 个总监 Agent + 1-2 个审计组 Agent |
| **汇报对象** | CEO（唯一） |
| **核心职责** | 对每个已完成任务进行独立审计，基于任务预设目标评分，行使通过/回滚权 |
| **输入** | 任务目标文档（执行前生成） + 任务交付物（执行后产出） + 执行日志 |
| **输出** | 结构化审计报告（评分 + 问题清单 + 通过/回滚判定 + 改进建议） |
| **权限** | 任何任务未通过质检审计不得进入下游环节或对外发布 |
| **不参与** | 任务目标制定、执行方案设计、执行过程干预 |

## 三、核心工作流：目标锚定 → 执行 → 审计 → 通过/回滚

### 3.1 流程全景

```
[任务启动]
    |
    v
Step 1: 定义任务目标（任务目标文档）
    |   - 具体交付物描述
    |   - 可衡量的验收标准
    |   - 关键项标记（不可妥协的质量底线）
    |   - 评分维度与权重
    |
    v
Step 2: 制定执行方案
    |   - 选择执行 Agent
    |   - 确定执行步骤
    |   - 预估工时和资源
    |
    v
Step 3: 执行任务
    |   - 执行 Agent 按计划执行
    |   - 记录执行日志（做了什么、遇到什么问题、做了什么决策）
    |
    v
Step 4: 交付审计
    |   - 执行 Agent 将交付物 + 执行日志提交给质检总监
    |   - 质检总监独立审计（不接触执行 Agent，只看交付物和日志）
    |
    v
Step 5: 审计判定
    |
    +-- [通过] ---> Step 6: 进入下游或交付客户
    |
    +-- [修订] ---> Step 5a: 质检总监出具问题清单
    |                    |
    |                    v
    |               执行 Agent 针对问题清单修订
    |                    |
    |                    v
    |               重新提交审计（回到 Step 4）
    |               [最多修订 2 轮，第 3 轮仍未通过 → 升级为回滚]
    |
    +-- [回滚] ---> Step 5b: 质检总监出具失败分析报告
                         |
                         v
                    CEO 审批回滚决策
                         |
                         v
                    重新制定执行方案（回到 Step 2）
                    [方案必须针对失败原因做出根本性调整]
```

### 3.2 三种审计判定

| 判定 | 条件 | 后续动作 |
|------|------|---------|
| **通过（PASS）** | 总分 >= 80 且无关键项不合格 | 进入下游环节或交付客户 |
| **修订（REVISE）** | 总分 60-79 或 有关键项"部分达标" | 执行 Agent 根据问题清单修订后重新提交，最多 2 轮 |
| **回滚（ROLLBACK）** | 总分 < 60 或 有关键项"严重不合格" 或 修订 2 轮仍未通过 | 废除当前执行方案，重新制定方案从头来过 |

### 3.3 回滚的三种情形与应对

| 回滚情形 | 根因分析 | 新方案要求 |
|---------|---------|-----------|
| **目标定义不清** | 任务目标含糊、验收标准模糊导致执行方向偏差 | 必须重写任务目标文档，增加具体量化指标和示例 |
| **执行方案有误** | 方案本身有根本缺陷（比如选错了工具、遗漏了关键步骤） | 必须更换执行方案的核心策略，不能只改细节 |
| **执行质量低劣** | 方案正确但执行不到位（比如 AI 产出质量不稳定） | 必须优化 Prompt、更换工具、或增加中间检查点 |

- [时间/资源/质量方面的硬性约束]

## 五、四类任务的差异化评分模板

### 5.1 产出物型任务（模板、文档、代码、图片、页面等）

| 评分维度 | 权重 | 评分标准 | 验证方式 |
|---------|------|---------|---------|
| **目标达成度** | 40% | 交付物是否满足任务目标文档中定义的每一条标准 | 逐条对照 |
| **完整性** | 20% | 交付物清单中的每一项是否齐全 | Checklist 检查 |
| **质量达标** | 25% | 技术质量（代码无报错、图片无变形、文档无拼写错误）+ 业务质量（品牌一致性、信息准确性） | 自动化工具 + 抽检 |
| **无副作用** | 15% | 是否破坏已有功能、引入新问题、违反品牌规范 | 回归检查 |

**典型任务示例**：
- T1-1（Canva 模板库）：关键项 = 模板数量 >= 50、品牌调性一致、覆盖 7 个平台尺寸
- K3-2（独立站 主题定制）：关键项 = Liquid 代码无语法错误、移动端适配、Lighthouse > 85
- K4-6（博客文章）：关键项 = SEO 关键词自然嵌入、字数 >= 1500、FABE 结构完整

### 5.2 流程型任务（配置、上架、数据抓取、部署等）

| 评分维度 | 权重 | 评分标准 | 验证方式 |
|---------|------|---------|---------|
| **步骤完整性** | 30% | SOP 中的每一步是否都已执行 | 执行日志逐步核对 |
| **步骤正确性** | 30% | 每一步的执行结果是否符合预期 | 抽样验证（30% 步骤） |
| **端到端可用** | 25% | 整个流程从头到尾能跑通 | 端到端测试 |
| **异常处理** | 15% | 遇到异常时是否按 SOP 处理、是否记录了异常信息 | 日志审查 |

**典型任务示例**：
- K3-1~K3-7（独立站 配置 13 项）：关键项 = 所有 13 项配置完成、结账流程端到端测试通过、支付网关实际扣款成功
- K3-8~K3-9（产品上架）：关键项 = 所有 SKU 上架、产品信息与源数据一致、图片加载正常
- A2-2（建站组 Agent 部署）：关键项 = Agent 能独立完成 独立站 配置 13 项、执行日志完整

### 5.3 决策型任务（策略制定、方案选择、架构设计等）

| 评分维度 | 权重 | 评分标准 | 验证方式 |
|---------|------|---------|---------|
| **逻辑自洽** | 30% | 决策依据是否充分、推理链是否完整 | 逻辑审查 |
| **备选方案** | 20% | 是否列出了至少 2 个备选方案及对比分析 | 文档检查 |
| **风险识别** | 25% | 是否识别了该决策的主要风险及应对方案 | 对照三大核心风险 |
| **可追溯性** | 25% | 决策过程是否有完整记录，事后能理解"为什么这样决定" | 记录审查 |

**典型任务示例**：
- K2-2（页面设计决策）：关键项 = 6 项决策均有明确理由、至少对比 2 个主题方案、符合品牌调性
- B3-1（定价验证）：关键项 = 有真实客户反馈数据、ROI 计算完整、对标竞品价格

### 5.4 持续型任务（监控、追踪、维护、优化等）

| 评分维度 | 权重 | 评分标准 | 验证方式 |
|---------|------|---------|---------|
| **执行频率** | 25% | 是否按预定频率执行（每日/每周/每两周/每月） | 执行记录时间戳 |
| **数据准确性** | 30% | 报告中的数据是否准确、是否有遗漏或错误 | 抽样核对源数据 |
| **趋势洞察** | 25% | 是否识别出异常趋势、是否给出了可执行的建议 | 报告内容审查 |
| **及时预警** | 20% | 出现异常时是否及时通知了相关负责人 | 通知记录审查 |

**典型任务示例**：
- R-11（SEO 排名追踪）：关键项 = 每两周准时执行、排名数据与 GSC 一致、排名下降 > 5 位时自动预警
- R-8（Prompt 优化）：关键项 = 每周记录优化内容、有优化前后对比数据、质量达标率有提升

## 七、质检 Agent 与现有工作流的整合

### 7.1 嵌入工作清单的审计检查点

工作清单中的每个任务项，现在需要增加一个"审计规格"字段：

| 字段 | 说明 |
|------|------|
| 审计类型 | 产出物审计 / 流程审计 / 决策审计 / 持续型审计 |
| 关键项 | 该任务中哪些验收标准是"不可妥协"的（标记为关键项） |
| 审计方式 | 全量审计（关键任务）/ 抽检 30%（常规任务）/ 抽检 10%（低风险任务） |
| 回滚触发条件 | 什么情况下直接回滚而非修订 |

### 7.2 按风险等级分配审计深度

| 风险等级 | 适用任务 | 审计深度 | 修订轮次 | CEO 介入 |
|---------|---------|---------|---------|---------|
| **P0 关键** | K-0（签约）、K4-4（产品页审核）、K5-1（支付测试） | 全量审计 + CEO 复核 | 最多 2 轮，第 3 轮回滚 | 审计通过也需 CEO 签字 |
| **P1 重要** | K1-7（品牌故事）、K3-2（主题定制）、K4-6（博客文章）、T2-2（行业模板） | 全量审计 | 最多 2 轮，第 3 轮回滚 | 仅回滚时介入 |
| **P2 常规** | K3-3（导航菜单）、K4-5（FAQ）、T1-1（模板创建）、A1-2（文案 Agent） | 抽检 30% | 最多 1 轮，第 2 轮回滚 | 仅回滚时知晓 |
| **P3 低风险** | K3-10（robots.txt）、K4-7（法律页面）、T3-4（Schema 代码） | 抽检 10% | 最多 1 轮，第 2 轮回滚 | 不介入，除非连续 3 次失败 |

### 7.3 CEO 审核比例的变化路径

| 阶段 | CEO 审核比例 | 质检 Agent 角色 |
|------|------------|---------------|
| 首位客户（Phase 1） | CEO 100% 复核质检 Agent 的审计结果 | 学习和校准：质检 Agent 与 CEO 并行审计，对比评分差异，校准评分标准 |
| Phase 2（5-10 客户） | CEO 审核 P0 关键任务 + 所有回滚决策（约 30%） | 独立运行：质检 Agent 独立审计 P1-P3 任务，CEO 信任其判断 |
| Phase 3（10-30 客户） | CEO 仅审核回滚决策 + 战略影响任务（约 10%） | 全面自主：质检 Agent 对所有任务行使终审权，CEO 只看审计报告摘要 |
| Phase 4（30-100 客户） | CEO 仅处理异常升级（约 5%） | 自动化闭环：质检 Agent + 异常处理 SOP 形成闭环，CEO 只看周报 |

## 八、质检 Agent 在 Agent 中的实现方案

### 8.1 技术实现路径

质检总监 Agent 在 Agent 中的实现方式：

| 组件 | 实现方式 | 说明 |
|------|---------|------|
| 任务目标文档 | Markdown 文件（存储在项目目录中） | 每个任务对应一个目标文档，审计时读取 |
| 审计触发 | Agent 子任务（Task 工具） | 执行 Agent 完成后，触发质检 Agent 子任务 |
| 评分执行 | LLM + 结构化输出 | 质检 Agent 读取目标文档 + 交付物，输出结构化审计报告 |
| 自动化验证 | Python 脚本 + 浏览器自动化 | 代码检查（Lighthouse/链接/拼写）用脚本自动跑，业务判断用 LLM |
| 审计报告 | Markdown 文件（存储在审计报告目录中） | 每份报告存档，供趋势分析和经验积累 |
| 回滚通知 | IM 通道推送 | 回滚判定时自动通知 CEO 审批 |

### 8.2 自动化验证工具箱

质检 Agent 应预装以下验证能力：

| 验证工具 | 适用场景 | 验证内容 |
|---------|---------|---------|
| Lighthouse API | 网页质量 | Performance / Accessibility / SEO / Best Practices 评分 |
| Link Checker | 网页链接 | 404 / 500 / 重定向链 |
| HTML Validator | 网页代码 | W3C 标准合规性 |
| Image Checker | 图片质量 | 尺寸合规、ALT 标签存在、文件大小合理 |
| Spelling Checker | 文案内容 | 拼写错误、语法错误 |
| SEO Checker | SEO 配置 | Meta Title/Description 存在且长度合规、Schema.org 标记有效 |
| Mobile Checker | 移动端适配 | 视口配置、触控目标尺寸、字体可读性 |
| API Test | 接口调用 | 状态码、响应时间、数据格式 |
| Data Validator | 数据准确性 | 源数据与目标数据一致性、字段完整性 |

### 8.3 审计报告的存档与分析

所有审计报告存放在项目目录下的 `审计报告/` 子目录中：

```
国际站卖家双轨出海OPC项目/
  审计报告/
    QA-2026-06-15-001_K3-2_主题定制.md
    QA-2026-06-15-002_K3-9_产品上架.md
    QA-2026-06-16-001_K4-6_博客文章_第2轮.md
    ...
```

质检 Agent 每月生成一份"审计月报"：
- 本月审计任务总数 / 通过率 / 修订率 / 回滚率
- 回滚任务的根因分布（目标不清 / 方案有误 / 质量低劣）
- 各执行 Agent 的质量得分趋势
- 评分标准校准建议

## 九、对工作清单的影响

### 9.1 新增审计相关任务

| 编号 | 工作项 | 预估工时 | 前置依赖 | 所属轨道 |
|------|--------|---------|---------|---------|
| QA-1 | 部署质检总监 Agent + 审计组 Agent | 3-5 天 | 无 | 轨道一（新增） |
| QA-2 | 开发自动化验证工具箱（Lighthouse/Link Checker/SEO Checker 等脚本） | 5-7 天 | QA-1 | 轨道一（新增） |
| QA-3 | 建立审计报告模板 + 存档目录结构 | 1 天 | QA-1 | 轨道一（新增） |
| QA-4 | 为现有工作清单的每个任务补充"任务目标文档" | 3-5 天 | 无 | 轨道一（新增） |
| QA-5 | 首位客户建站全程审计（与 CEO 并行，校准评分标准） | 贯穿首位客户建站 | QA-1 ~ QA-4 | 轨道二（嵌入） |
| QA-6 | 审计月报自动生成脚本 | 2 天 | QA-3 + 有审计数据后 | 轨道四（新增） |

### 9.2 现有工作流变更

每个任务的执行流程从原来的"执行 → 人工审核 → 交付"变为"定义目标 → 执行 → 质检 Agent 审计 → 通过/修订/回滚 → 交付"。具体变更：

- **轨道一**所有任务：增加"定义任务目标"步骤和"质检 Agent 审计"步骤
- **轨道二**关键路径：每个 K 系列任务完成后自动触发质检 Agent 审计，审计通过后才能进入下一阶段
- **轨道四**Agent 部署：每个 Agent 部署后需通过质检 Agent 的"能力验收审计"（给 Agent 一个测试任务，审计其产出质量）

### 9.3 关键路径时间影响

增加独立审计环节后，首位客户建站的关键路径时间会有所延长：

| 阶段 | 原预估 | 加审计后预估 | 增加原因 |
|------|--------|------------|---------|
| 阶段一（需求收集） | Day 1-2 | Day 1-3 | K1-7（品牌故事）需审计 |
| 阶段二（信息架构） | Day 2-3 | Day 3-4 | K2-1 ~ K2-3 需审计 |
| 阶段三（技术搭建） | Day 3-5 | Day 4-7 | K3-2/K3-9/K3-10 需审计 + 可能修订 |
| 阶段四（内容填充） | Day 5-7 | Day 7-10 | K4-1 ~ K4-7 需审计，K4-8 验收需审计 |
| 阶段五（上线交付） | Day 7 | Day 10-11 | K5-1 上线 Checklist 需审计 |
| **总计** | **7 天** | **11 天** | **增加约 60%，但质量保障显著提升** |

**注**：首位客户之后，随着审计标准校准完成和修订率下降，后续客户建站时间预计可压缩至 5-7 天（含审计）。

## 十、审计 Agent 的"三大风险"专项检查

质检 Agent 除了技术性审计外，还需要在每个任务的审计中嵌入三大核心风险的检查项：

| 风险 | 审计检查项 | 触发条件 |
|------|---------|---------|
| **行业信任赤字** | 该任务的产出物是否有真实数据/案例支撑？是否存在"过度承诺"？ | 所有面向客户的交付物 |
| **付费意愿不确定** | 该任务的产出是否能在 30 天内让客户看到可感知的价值？ | 所有涉及客户交付的任务 |
| **平台下场风险** | 该任务建立的能力是否独立于阿里生态？如果阿里明天推出同类服务，这个产出还有价值吗？ | 所有涉及能力建设的任务 |

任何任务如果在三大风险检查项中触发"红色警报"，即使技术评分达标，质检 Agent 也有权在审计报告中附加"战略风险提示"，要求 CEO 在交付前审阅。
