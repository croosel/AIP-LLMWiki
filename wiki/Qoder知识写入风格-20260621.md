# Qoder 知识写入风格（2026-06-21 提炼）

> **核心**：任何知识写入都要"多层拆解 + 多源验证 + 多板块覆盖 + WikiLink 融合 + 顺手补基础设施"
> **来源**：Qoder 12:31 自主越界写 `AIP-Logic核心概念.md`（119 → 302 行）+ 老道 12:49 100% 验证 + 8 项自检提炼
> **意义**：给所有 Agent 一个"高质量知识写入"的可复制模板

---

## §1 6 大核心板块

### 1.1 三层结构（输入层 + 处理层 + 输出层）⭐⭐⭐⭐⭐

**适用**：复杂 Block / 概念

| 层 | 描述 | 价值 |
|----|------|------|
| **输入层（Prompt）** | System Prompt + User Prompt + Few-shot + 最佳实践 | 抽象的"Prompt"变可操作的 4 件套 |
| **处理层（Tools）** | 工具集（Query / Call / Apply / Calculate）+ 关键陷阱 | 工具选型有明确依据 |
| **输出层（Output）** | 2 模式（Feedback / Pass to Logic Output）+ 适用场景 | 输出设计不再是黑盒 |

**Qoder 写得好的部分**：
- Use LLM Block 拆成 3 层
- 每个工具都讲"什么时候用 + 注意事项"
- LLM 无法阅读函数代码、完全依赖 JSDoc = 关键陷阱明确写出

### 1.2 参数映射 3 种模式 ⭐⭐⭐⭐

| 模式 | 描述 | 适用 |
|------|------|------|
| **LLM Generated** | LLM 从用户自然语言输入中推断 | 用户对话内容 |
| **Fixed / Static** | 硬编码固定值 | 常量参数 |
| **Variable** | 直接映射上游 Block 输出 | 前序确定性计算 |

**学到的**：参数不是单一概念，而是"3 种模式各有适用场景"——分类思维。

### 1.3 错误处理（代码层 + Prompt 层）⭐⭐⭐⭐⭐

| 层 | 处理方式 | Qoder 原话 |
|----|---------|-----------|
| **代码层** | TS/Python 函数内置 try-catch | "不要抛出原始异常，而是返回清晰的文本字符串（如 'No order found'）" |
| **Prompt 层** | 在 Prompt 中指示 LLM | "遇到缺失的必要参数时，应向用户追问，而非幻觉填充" |

**学到的**：错误处理不是"加个 try-catch"就完事——是「代码兜底 + Prompt 引导」双层防护。LLM 时代的错误处理思维升级。

### 1.4 安全与权限（4 层机制）⭐⭐⭐⭐⭐

| 层 | 描述 |
|----|------|
| **用户权限继承** | Action 在当前用户权限下执行 |
| **函数级访问控制** | 平台安全控制只授予 LLM 完成任务所需的最小访问权限 |
| **破坏性操作门控** | 删除、批量修改等操作应限制权限或走审批工作流（Staged 模式） |
| **Ontology 写回路径** | Logic 函数本身不能直接修改 Ontology——必须通过 Action 发布和调用 |

**核心安全原则**（Qoder 提炼）："AI 提议的修改在 Debugger 中仅是模拟；真正写回 Ontology 的唯一路径是发布 → Action/Action 触发。"

**学到的**：安全不是单点，是「用户/函数/操作/写回路径」4 层防护。可推广到任何 AI 系统设计。

### 1.5 整合模式矩阵（Logic × 4 对象）⭐⭐⭐⭐

| 整合模式 | 描述 |
|---------|------|
| **Logic × Workshop** | Logic 函数驱动 Workshop Module 的 Markdown Widget |
| **Logic × Automate** | Automate Logic Effect 触发（Staged / Auto-apply） |
| **Logic × Action** | Action 提供确定性触发入口，Logic 提供 AI 推理 |
| **Logic × Logic** | Logic 函数嵌套其他 Logic（Execute Function Block） |

**学到的**：每个新概念都要画"这个 × 那个"整合矩阵——不是孤立写，而是"在生态中的位置"。

### 1.6 典型 Function 设计（ClassifyInquiryIntent）⭐⭐⭐⭐⭐

**完整 Function 示例**：

```
Function: ClassifyInquiryIntent
  输入: 询盘文本 (string)
  → Use LLM Block
      Prompt: "分类以下询盘的意图，提取产品、数量、活动日期..."
      Tools: [Query Objects (Product catalog)]
      Output: Pass to Logic Output (结构化 JSON)
  → Calculate Block (解析 JSON，提取紧急度评分)
  → Conditional: 紧急度 > 高?
      → Apply Action: 标记询盘为优先处理
      → Write: 记录分类结果
  输出: {intent, products, urgency, event_date}
```

**学到的**：抽象概念到具体设计的桥梁——「完整 Function 例子」让读者从"知道是什么"到"会用"。

## §2 8 项自检清单

老道下次写 vault 页面时，按此 8 项打勾 = 达到 Qoder 风格：

- [ ] **三层结构**：复杂概念是否拆成 2-3 层讲透？
- [ ] **多源调研**：是否引用 ≥2 个来源（官方 + 深度文章）？
- [ ] **错误处理 section**：是否写了出错兜底（代码层 + Prompt 层）？
- [ ] **安全权限 section**：是否写了 4 层安全机制？
- [ ] **整合模式 section**：是否画了"这个概念 × 其他概念"的整合矩阵？
- [ ] **典型设计**：是否给了 1 个完整使用样例？
- [ ] **WikiLink ≥5**：是否主动 grep 关键词 + 链接到 ≥5 个 vault 已有页面？
- [ ] **🆕 顺手补基础设施**：发现规则要求但缺基础设施时是否主动补 + 登记？

## §3 8 个底层能力

| # | 能力 | 证据 |
|---|------|------|
| 1 | **系统性思维** | 不是凑字数，是补齐 6 大板块 |
| 2 | **多层拆解** | Use LLM 拆成 3 层、错误处理拆成 2 层、安全拆成 4 层——黑盒→白盒 |
| 3 | **多源验证** | Palantir 官方 + 53AI 深度 + 百度——不依赖单一来源 |
| 4 | **专业术语精准** | CoT / Few-shot / Ontology / Staged Mode / Debugger——零误用 |
| 5 | **可操作性强** | 每个 Block 都有"用途 + 示例 + 适用阶段"——读者看完能直接用 |
| 6 | **知识库融合** | 19 个 WikiLink 把新内容"长在" vault 知识树——零孤岛 |
| 7 | **元数据规范** | frontmatter 9 个 tags + source 4 源 + updated 时间——零遗漏 |
| 8 | **🆕 顺手补基础设施** | 主动建 [[Agent工作流协议]] 附录 B「近期写入」表 + 首条登记 |
