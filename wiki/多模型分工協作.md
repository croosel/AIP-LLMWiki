# 多模型分工協作

> Scout-then-Swarm 的核心技術創新不在於多模型調用本身，而在於**基於模型長處的分工**——每個模型做不同的子任務，而非做相同的事再投票。本頁面詳述分工協作的技術細節、模型能力矩陣、角色分配、交叉驗證機制，以及與現有框架的比較。

## 分工 vs 投票：根本性差異

### Ensemble Voting（[[Model-Fusion分析]] 的做法）

```
用戶任務 → [Model A 完整回答] ┐
          → [Model B 完整回答] ├→ 投票/融合 → 最終答案
          → [Model C 完整回答] ┘
```

- 三個模型做**同一件事**
- 最終結果不過是某一個模型本來就能產出的
- 浪費 2/3 的 token
- 品質上限 = 最佳單模型

### Division of Labor（Scout-then-Swarm 的做法）

```
用戶任務 → Orchestrator 拆解 → [子任務 1 → Model A（擅長此類）] ┐
                              → [子任務 2 → Model B（擅長此類）] ├→ 交叉驗證 + 加權融合 → 最終答案
                              → [子任務 3 → Model C（擅長此類）] ┘
```

- 每個模型做**不同的事**，基於各自長處
- 最終結果是任何單個模型都產不出的
- Token 花在刀口上
- 品質上限 > 任何單模型

## 交叉驗證機制

### 核心原則

**生產者不可驗證自己的輸出。** 這是交叉驗證的鐵律。

### 驗證路由表

| 生產模型 | 驗證模型 |
|---------|---------|
| deepseek-v4-pro | qwen-37-max |
| kimi-k27-code | qwen-37-max |
| minimax-m3 | deepseek-v4-pro |
| qwen-37-max | deepseek-v4-pro |

```python
def _pick_verifier(worker_model: str, default_judge: str) -> str:
    """驗證模型必須與生產模型不同。"""
    if worker_model == default_judge:
        return "deepseek-v4-pro"   # Qwen 生產 → DeepSeek 驗證
    return default_judge            # 其他 → Qwen 驗證
```

### 加權融合算法

權重公式：**w_i = 0.4 * self_confidence + 0.6 * verification_score**

60/40 分配偏向獨立驗證，因為模型自我報告的置信度傾向過度自信。

```python
def _compute_weights(responses, verifications):
    SELF_W, VERIFY_W = 0.4, 0.6
    verify_map = {v.subtask_id: v for v in verifications}
    weights = []
    for r in responses:
        v = verify_map.get(r.subtask_id)
        verify_score = v.check.overall_confidence if v else 0.5
        raw = r.confidence * SELF_W + verify_score * VERIFY_W
        weights.append(WeightInfo(
            subtask_id=r.subtask_id,
            raw_confidence=r.confidence,
            verification_score=verify_score,
            final_weight=raw
        ))
    # 正規化
    total = sum(w.final_weight for w in weights)
    for w in weights:
        w.final_weight = w.final_weight / total if total > 0 else 1.0 / len(weights)
    return weights
```

### 法定人數收斂條件

三條件同時滿足才收斂：

1. 領先方向的置信度 >= 0.6
2. 領先方向的置信度是第二名的 1.5 倍以上
3. 紅隊沒有標記任何致命缺陷

## 經驗回饋閉環

經驗系統讓分工協作隨著使用越來越好。閉環機制：

```
執行前：查詢經驗庫 → 使用歷史分解模板
執行中：記錄關鍵決策和結果
執行後：沉澱成功經驗 → 更新置信度
```

### 經驗生命周期

1. 任務成功 → 寫入經驗庫（TTL = 90 天，model_versions = 當前版本）
2. 被後續使用 → sample_size++，置信度加權更新
3. 模型版本變更 → stale = TRUE，置信度 *= 0.5
4. 連續失敗 3 次 → 刪除
5. 過期 → 歸檔

### 強制探索

防止經驗庫陷入局部最優：每 10 次執行強制 1 次不使用經驗庫（exploration rate = 10%）。新策略若效果更好 → 寫入為新經驗。

### 經驗庫 Schema

```sql
CREATE TABLE experiences (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    task_summary    TEXT NOT NULL,
    task_hash       TEXT NOT NULL,
    subtask_types   TEXT,                 -- JSON array
    execution_mode  TEXT,                 -- swarm | pipeline | checkpoint
    outcome         TEXT,                 -- success | partial | failure
    confidence      REAL,                 -- 0.0-1.0
    lesson          TEXT,
    model_versions  TEXT,                 -- JSON {role: model_version}
    sample_size     INTEGER DEFAULT 1,
    created_at      TEXT NOT NULL,
    expires_at      TEXT,                 -- 90 天 TTL
    raw_output      TEXT
);
```

## 與現有框架對比

| 維度 | Scout-then-Swarm | LangGraph | CrewAI | AutoGen |
|------|-----------------|-----------|--------|---------|
| **定位** | Blueprint（可 clone 的 Graph 模板） | 通用狀態機引擎 | Agent 角色框架 | 多 Agent 對話框架 |
| **任務分解** | 模板匹配 + 結構化輸出 + 覆核檢查 | 用戶自行實現 | 內建 Task 分配 | 群聊自動分配 |
| **決策融合** | 加權融合 + 交叉驗證 + 結構化辯論 | 用戶自行實現 | 順序/並行 + 委派 | 對話式共識 |
| **經驗系統** | SQLite + TTL + 強制探索 + GC | Checkpoint（無經驗學習） | 無 | 無 |
| **模型分工** | 按子任務類型路由到最佳模型 | 用戶自行配置 | 按角色配置 | 按 Agent 配置 |
| **快速通道** | 規則引擎 < 50ms 分類 | 無 | 無 | 無 |
| **成本透明** | 每次任務顯示實際成本 | 透過 LangSmith | 無 | 無 |
| **差異化價值** | 擺尾舞決策算法 + 經驗學習閉環 + 任務模板庫 | 基礎設施完善 | 易用性 | 對話式協作 |

### 核心差異

Scout-then-Swarm **不做框架**，而是 LangGraph 上的一個 Blueprint。價值在應用層（模板庫 + 辯論協議 + 經驗系統），不在基礎設施層。

| 我們提供 (Blueprint) | LangGraph 已有 (不重複造輪子) |
|---------------------|------------------------------|
| 任務分解模板庫 | StateGraph 狀態機引擎 |
| 擺尾舞協議實現 | Checkpoint / Persistence |
| 經驗系統 schema + 邏輯 | Streaming / Tool calling |
| Fast-Track Gate 規則 | Human-in-the-loop |
| 模型分工配置 | Error handling primitives |
| 成本估算與監控 | LangSmith tracing integration |

## LiteLLM 統一調用層

所有模型透過 LiteLLM 統一調用，而非各模型原生 SDK：

```python
from litellm import acompletion

response = await acompletion(
    model="openai/deepseek-reasoner",  # LiteLLM 格式
    api_base="https://api.deepseek.com",
    messages=[{"role": "user", "content": task}],
    max_tokens=4096,
)
```

選擇 LiteLLM 而非 `agentfw`（見 [[Model-Fusion分析]]）的理由：
- 標準的 OpenAI-compatible API 封裝
- 與 LangGraph 生態相容
- 支援 fallback 和 retry 機制
- 社群活躍，持續維護
