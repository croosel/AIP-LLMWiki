# Scout-then-Swarm 架構

> **架構哲學**：不是 ensemble voting（冗餘投票），而是真正基於 LLM 長處的分工協作。
> 用模板匹配 + 第一性原理拆解任務，用蜂群分工執行，用交叉驗證融合結果，用經驗累積持續進化。

## 起源

Scout-then-Swarm 的靈感來自 OpenRouter 的 [Model Fusion](Model-Fusion分析) 方案——透過 `agentfw` 本地代理將多個 LLM 並行調用，再用集成投票融合結果。然而深入分析後發現，**ensemble voting 浪費了 2/3 的 token**：三個模型回答同一個問題再投票選最佳，本質上是冗餘而非協作。

關鍵轉折：從「投票」走向「分工」。借鑒蜜蜂蜂群的決策機制——3-5% 的經驗偵查蜂先偵查、搖擺舞溝通、交叉驗證、法定人數收斂——發展出一套**基於分工的多模型協作架構**。詳見 [[蜂群決策映射]]。

## 核心原則

### 分工，不投票

每個模型基於自身長處接收**不同的**子任務，而非三個模型做同一件事再選最好的。分工產出的最終結果，是任何單個模型都產不出的東西。參見 [[多模型分工協作]]。

### 任務類型感知的評估策略

審稿蜂指出原「第一性原理評估」對開放式創意任務無效。改為按任務類型路由評估策略：

| 任務類型 | 評估策略 | 具體檢查項 |
|---------|---------|----------|
| 分析型（analytical） | 一階原則 | 邏輯自洽？覆蓋所有要求？有事實錯誤？推導完整？ |
| 程式碼（code） | 可執行性 | 能編譯/執行？處理邊界？符合框架版本？有安全漏洞？ |
| 創意型（creative） | 約束符合性 | 符合風格/調性？滿足長度/格式？有 AI 味？偏離主題？ |

任務類型在模板匹配階段確定，不依賴 Orchestrator 即時判斷。

### 經驗引導搜索

Orchestrator 先搜 Wiki 經驗庫，用過去的任務拆解模式作為起點，再用第一性原理校驗適用性。經驗決定往哪看，第一性原理決定看到之後怎麼判斷。

### 結構化辯論收斂

審稿蜂指出原「搖擺舞正反饋」有馬太效應風險。改為結構化辯論協議：好的方向經過紅隊質詢後仍然成立才吸引更多資源，差的方向被質疑後自然衰減。防馬太效應機制包括：

- 置信度上限 0.8（保留不確定性）
- 強制紅隊質詢（每個方向都必須被挑戰）
- 衰減函數（未被再次確認的方向權重自然下降）
- 20% 最低探索預算

### 藍圖而非框架

不做獨立框架，定位為 **LangGraph Blueprint**。不封裝 LangGraph 已有的原語（StateGraph, nodes, edges），價值在於：任務分解模板庫 + 結構化辯論協議 + 經驗系統。發布形式為可 clone 的 LangGraph Blueprint 專案。

## 四階段架構

```
Scout（偵查）→ Swarm（蜂群執行）→ Verify（交叉驗證）→ Learn（經驗回寫）
```

### Stage 1: Scout（偵查）

Orchestrator（DeepSeek V4 Pro）負責任務分析和拆解。流程：

1. **Fast-Track Gate**：純規則引擎，50ms 內判斷任務複雜度。80% 的任務走快速通道，單模型直達
2. **經驗庫搜尋**：查詢 SQLite + FTS 是否有相似任務的歷史分解
3. **模板匹配**：命中經驗用歷史模板，未命中用預定義模板中最近似的
4. **分解覆核檢查**：完整性、無環性、可驗證性、模型匹配、子任務數量 <= 8

### Stage 2: Swarm（蜂群執行）

Worker Bees 透過 LiteLLM 並行調用，按子任務類型路由到最佳模型。三種執行模式：

- **Swarm 模式**（低耦合）：子任務完全獨立，全部平行執行
- **Pipeline 模式**（高耦合）：子任務有線性依賴，順序執行 + Checkpoint 驗證
- **Checkpoint 模式**（混合）：階段內平行，階段間順序

耦合度判斷為三級（非二元）：`output_deps == 0` → Swarm；`<= nodes * 0.3` → Checkpoint；else → Pipeline。不確定時預設 Pipeline（寧可慢，不要錯）。

### Stage 3: Verify（交叉驗證）

核心原則：**生產者不可驗證自己的輸出。** 驗證路由表：

| 生產模型 | 驗證模型 |
|---------|---------|
| deepseek-v4-pro | qwen-37-max |
| kimi-k27-code | qwen-37-max |
| minimax-m3 | deepseek-v4-pro |
| qwen-37-max | deepseek-v4-pro |

加權融合算法：**w_i = 0.4 * self_confidence + 0.6 * verification_score**

60/40 分配偏向獨立驗證，因為模型自我報告的置信度傾向過度自信。

### Stage 4: Learn（經驗回寫）

成功經驗沉澱到 SQLite 經驗庫（TTL = 90 天），帶 `model_version` 追蹤。模型版本變更時舊經驗自動標記為 `stale`，置信度 *= 0.5。連續失敗 3 次 → 刪除。

## 模型陣容

| 角色 | 模型 | 負責的任務類型 |
|------|------|--------------|
| 排程蜂 (Orch.) | DeepSeek V4 Pro | 任務分解、推理、分析 |
| 長文蜂 (LongDoc) | MiniMax M3 | >50K tokens、文件分析 |
| 碼蜂 (Coder) | Kimi K2.7 Code | 程式碼生成/修改/審查 |
| 結構蜂 (Struct) | Qwen 3.7 Max | 結構化輸出、JSON、表格 |
| 裁判蜂 (Judge) | Qwen 3.7 Max | 交叉驗證紅隊、最終綜合 |
| 推理蜂 (Reasoner) | DeepSeek V4 Pro | 數學、邏輯、分析 |

定價詳情見 [[Model-Fusion分析]]，能力矩陣見 [[多模型分工協作]]。

## 關鍵架構決策

| 決策 | 選擇 | 理由 |
|------|------|------|
| 任務分解方式 | 模板匹配 > 自由分解 | 審稿蜂致命風險 O1：自由分解錯誤 → 全線垃圾進垃圾出 |
| 決策收斂方式 | 結構化辯論 > 搖擺舞正反饋 | 審稿蜂嚴重風險 W1：純正反饋有馬太效應 |
| 定位 | LangGraph Blueprint > 獨立框架 | 審稿蜂風險 P1：與現有框架無本質差異 |
| MVP 範圍 | 一個週末驗證一個假說 | 審稿蜂風險 M1：MVP 範圍過大 |
| 執行模式 | 三種模式 + 預設保守 | 審稿蜂風險 C1：耦合度判斷錯誤 |
| 快速通道 | 80% 任務走 Fast-Track | 審稿蜂風險 D1：延遲 3-5 倍 |

## MVP 策略

> **核心假說**：cross-verification + weighted fusion 顯著優於 simple ensemble。
> **時間框架**：一個週末。
> **成功判據**：預定義，不可事後移動龍門。

### MVP 範圍

| 階段 | 做什麼 | 不做什麼 |
|------|--------|---------|
| Scout | 3 個固定模板 + 模板匹配 | 自由形式分解 |
| Swarm | 2-3 個 Worker 並行（Swarm 模式 only） | Pipeline / Checkpoint |
| Verify | 交叉驗證 + 第一性原理檢查 | 任務類型感知路由（Phase 2） |
| Fuse | 加權融合（0.4 self + 0.6 verify） | 擺尾舞（Phase 2） |
| Learn | SQLite 基本 CRUD + 90 天 TTL | 強制探索、GC（Phase 2） |
| Benchmark | 100 任務 A/B 測試 | 人類盲評（Phase 2） |

### 成功標準

| 指標 | 目標 | 測量方式 |
|------|------|----------|
| 品質提升 | swarm_judge confidence 比 baseline 高 >= 5% | Mann-Whitney U test |
| 統計顯著性 | p < 0.05 | 雙尾檢定 |
| P95 延遲 | < 15 秒 | 100 個任務的 P95 |
| Fast-Track 準確率 | 簡單任務 100% 被分類 | 30 個簡單任務命中數 |
| 錯誤率 | < 5% | 100 個任務中失敗數 |
| 平均成本 | < $0.10 USD / 任務 | 總成本 / 100 |

**Go 條件**：6 項全部達成。**No-Go 條件**：任何 1 項未達成 → 停止或重新設計。

### 分階段路線圖

- **Phase 0**（一個週末）：核心假說驗證，100 任務 A/B 基準測試
- **Phase 1**（一個月）：加入 Pipeline + Checkpoint，擴展模板庫到 10+
- **Phase 2**（三個月）：擺尾舞協議、強制探索、動態模式切換、LangSmith 整合
- **Phase 3**（持續）：多租戶經驗庫、模型能力矩陣自動更新

## 風險地圖

### 致命風險（1 項）

- **O1** Orchestrator 任務拆解錯誤 → 全線垃圾進垃圾出。應對：模板匹配 + 分解覆核檢查 + 降級到 Pipeline

### 嚴重風險（5 項）

- **E1** 第一性原理評估對開放式任務無效 → 任務類型感知評估策略
- **W1** 擺尾舞正反饋放大早期錯誤 → MVP 禁用，Phase 2 採用結構化辯論
- **X1** 經驗過時 / 錯誤經驗擴散 → TTL + model_version + 強制探索
- **C1** 耦合度判斷錯誤 → 三級耦合 + 預設保守 + 動態模式切換
- **D1** 延遲 3-5 倍 + 成本 5 倍 → Fast-Track + 延遲預算 + 成本紅線

## 成本估算

以程式碼審查為例：
- Orchestrator 分解: ~500 tokens out → ¥0.003
- Kimi K2.7 靜態分析: ~2K in, ~1K out → ¥0.04
- DeepSeek V4 邏輯審查: ~2K in, ~1K out → ¥0.012
- Qwen 3.7 綜合: ~3K in, ~1.5K out → ¥0.045
- **總計: ~¥0.12 / 次**（對比單模型 Qwen Max ~¥0.066，約 1.8 倍）
- **成本紅線**: 單次任務不超過 ¥0.50

## 四蜂產出與交叉驗證

本架構由四個「蜂」協作完成，經過交叉驗證：

| 蜂 | 核心產出 | 關鍵貢獻 |
|-----|---------|---------|
| 偵查蜂 | Wiki 172 檔案全量掃描 | 先驗知識基礎、角色映射、7 條設計原則 |
| 建築蜂 | 完整系統架構設計 | Fast-Track Gate、結構化辯論、模板匹配 |
| 工程蜂 | MVP 實作計畫 | swarm_judge() 入口、加權融合算法、A/B 基準測試 |
| 審稿蜂 | 第一性原理攻擊 | 1 致命 + 5 嚴重 + 2 可控風險 |

四蜂一致性檢查結果：MVP 核心假說、模型角色分配、執行模式、Fast-Track、經驗系統、LangGraph 定位全部**一致**。擺尾舞為**有條件一致**（Phase 2 採用結構化辯論版）。
