# 独立站产品上架工作流架构

## 定义

独立站产品上架工作流是一套从阿里巴巴国际站（ICBU）批量复制产品到 Next.js 独立站的端到端工程体系。基于第一性原理，工作流按职能边界划分为"运营层"（Agent）和"工程层"（Agent IDE），以 QC 审计 Agent 为质量关卡（评分 ≥80 方可放行），实现可复制、可审计、可回滚的自动化产品上架。

## 核心原则

### 第一性原理分工

| 层级 | 执行者 | 职责边界 | 核心能力 |
|------|--------|----------|----------|
| **运营层** | Agent | 数据准备、清洗、分类、QC 审计、流程编排 | API 调用、数据处理、文件生成、质量审计 |
| **工程层** | Agent IDE | 代码修复、构建测试、Git 管理、部署上线 | 源码编辑、TypeScript、Next.js、Vercel |
| **质量层** | QC Agent | 每个阶段节点的独立审计 | 数据完整性检查、代码审查、线上验证 |

### QC 关卡机制

工作流共设 12 道 QC 关卡，每道关卡按 100 分制评分，≥80 分方可进入下一阶段：

| 关卡 | 阶段 | 检查内容 | 满分 | 通过线 |
|------|------|----------|------|--------|
| QC-01 | 数据导出 | ICBU API 数据完整性（359 产品全覆盖） | 100 | 80 |
| QC-02 | 描述清洗 | Description 无 boilerplate、质量达标 | 100 | 80 |
| QC-03 | 产品分类 | 所有产品归入正确品类（0 uncategorized） | 100 | 80 |
| QC-04 | 定价数据 | 三级价格体系完整、MOQ 合理 | 100 | 80 |
| QC-05 | 库存数据 | inventory.json 覆盖全部产品 ID | 100 | 80 |
| QC-06 | 图片资产 | 359 张产品图 + 10 张分类图全部到位 | 100 | 80 |
| QC-07 | 代码阻断 | ProductCard/PDP 图片渲染、面包屑链接 | 100 | 80 |
| QC-08 | 构建通过 | TypeScript 编译 + Next.js build 零错误 | 100 | 80 |
| QC-09 | 部署成功 | Vercel 部署状态 Ready | 100 | 80 |
| QC-10 | 分类页验证 | 10 个品类页面产品数和图片正确 | 100 | 80 |
| QC-11 | PDP 验证 | 产品详情页图片/价格/库存/面包屑正确 | 100 | 80 |
| QC-12 | 端到端回归 | 全站功能回归测试 | 100 | 80 |

## 工作流阶段

### Phase 1：数据导出（Agent）

**Skill**: `icbu-product-export`

1. 调用 `alibaba.icbu.product.list` 获取全部产品元数据
2. 逐产品调用 `alibaba.icbu.product.get` 获取完整详情
3. 输出：`icbu_full_details.json`（API 原始响应缓存）
4. **QC-01 关卡** → 评分 ≥80 进入 Phase 2

### Phase 2：数据处理（Agent）

**Skill**: `icbu-data-processing`

1. ICBU 字段映射为 lilisaura Product 接口
2. 两遍 Description 清洗：去 boilerplate + 补空描述
3. 79 个未分组产品的关键词分类
4. 生成 `products.json`、`categories.json`
5. **QC-02/03/04 关卡** → 评分 ≥80 进入 Phase 3

### Phase 3：资产准备（Agent）

**Skill**: `inventory-generation`

1. 下载 359 张产品主图到 `public/images/products/`
2. 下载 10 张分类 hero 图到 `public/images/categories/`
3. 生成 `inventory.json`（每个产品 LA+DALLAS 双仓库）
4. 生成 `lilisaura_product_catalog.csv`
5. **QC-05/06 关卡** → 评分 ≥80 进入 Phase 4

### Phase 4：运营→工程交接（Handoff）

**交接文件**: 部署 Prompt + QC 报告 + SOP 工作表

Agent 向 Agent IDE 交接以下物料：
- 代码阻断项清单（ProductCard/PDP/breadcrumb/inventory）
- 修复方案（含代码片段）
- QC-06 通过报告
- `产品上架SOP工作表单.xlsx`

### Phase 5：工程实施（Agent IDE）

**Prompt**: `qoder-cn-engineering-prompt.md`

1. 初始化 Git 仓库，创建 `feat/product-catalog` 分支
2. 修复 4 个 CRITICAL 代码阻断项
3. 修复 3 个 MEDIUM 问题（筛选器/视图切换/导航栏）
4. TypeScript 编译检查
5. Next.js 构建验证
6. **QC-07/08 关卡** → 评分 ≥80 进入 Phase 6

### Phase 6：部署上线（Agent IDE）

1. Git commit + push
2. Vercel CI/CD 自动构建
3. 部署状态确认（Ready）
4. **QC-09 关卡** → 评分 ≥80 进入 Phase 7

### Phase 7：线上验证（Agent + QC Agent）

1. 浏览器自动化验证各品类页面
2. 验证产品详情页图片/价格/库存/面包屑
3. 产品数量核对（359 个全覆盖）
4. **QC-10/11/12 关卡** → 评分 ≥80 项目完成

| `icbu_full_details.json` | 缓存 | ICBU API 原始响应 |

| `qoder-cn-engineering-prompt` | Prompt | 工程层部署指令 |

## 关键教训

1. **Vercel CLI 直推 vs Agent IDE 工程化部署**：前者适合快速验证，后者符合第一性原理（有 Git 回滚、CI/CD、代码审查）
2. **代码阻断项应在开发阶段发现**：ProductCard 和 PDP 的 Package 图标占位符是开发阶段技术债，应在工程层而非运营层修复
3. **QC Agent 必须独立于执行层**：执行者不应自审，QC 审计必须由独立 Agent 执行
